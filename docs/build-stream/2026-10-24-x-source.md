## Plan overview

### Problem
Much of the AI frontier surfaces on X first: researchers announce papers, small labs drop models, and people
discuss results before anything reaches arXiv listings, blogs or Hugging Face. The radar can't see any of it.
The owner wants X ingested the way the rest of the radar works: follow the people behind frontier items, follow
whoever *they* follow, and keep growing toward novelty.

### Outcome (Working Backwards)
> *Frontier Radar now listens to X.* It watches the researchers and labs it already tracks on X. It picks up
> their posts about papers, models, repos and results, and resolves every link to the canonical item, so an
> arXiv paper shared by five strong researchers on its first day scores higher than one nobody noticed. It
> grows the watchlist through the X follow graph, weighting accounts that many productive accounts follow.
> It only uses sanctioned access and never spends past a configured cap.

**Hard FAQs**
- *Why not scrape x.com?* X's terms bar crawling and scraping without written consent, with stated liquidated
  damages, and scraping needs logged-in accounts (credentials). Off the table (DEC-2).
- *Which access paths?* (1) the **official X API v2**, pay-per-use since Feb 2026 (about $0.005 per post read,
  $0.010 per user read); (2) **xAI's `x_search`** server-side tool via the Responses API ($5 per 1k posts
  fetched plus tokens), which covers semantic discovery queries the X API can't do cheaply.
- *How is hallucination prevented with Grok?* Grok returns structured JSON, but a post is accepted only if
  its status URL is among the response's citations (citation-grounded extraction).
- *How is cost bounded?* Per-run read caps plus a daily USD cap tracked in the store. With no credentials the
  provider is `none` and nothing is spent.

### Goal / non-goals
- **Goals:** X provider layer (xapi, xai, none, auto); X handles on entities; watched-account timelines and
  configured lists; discovery queries; link → canonical item resolution with X engagement; follow-graph and
  co-follow expansion; handle discovery from GitHub profiles; researcher-attention novelty signal; spend caps;
  seeds; docs; tests.
- **Non-goals:** scraping or browser automation of x.com; posting to X; real-time streaming; OAuth user
  context. A user's own lists work through the app bearer token if the lists are public.

### Appetite
One focused session. Standard-to-Full ceremony, because of credentials and spend.

### Doc impact
README (X setup), docs/ARCHITECTURE.md (source + expansion), docs/NOVELTY.md (`attention`), CLAUDE.md
(handle `x`), `.env.example`, `config/radar.yaml`, `config/seeds.yaml`.

### Rollback
`x.provider: none` in config disables everything. The change is additive; reverting the files restores the
previous behaviour. The new `attention` feature defaults to 0 with no X data.

### Risks
Spend overrun (mitigated by caps); Grok hallucinating posts (citation grounding); wrong seed handles (resolved
via user lookup and marked invalid); weight drift from the new feature (prior weight is small and calibration
re-fits it).

## Design (S1)

**Provider layer** `radar/sources/x.py`
- `XClient` protocol: `user_posts(handle, since)`, `list_posts(list_id, since)`, `search(query, since)`,
  `following(handle, limit)`, `lookup(handles)`. Each returns normalised `XPost` / `XUser` dicts.
- `XApiClient` (bearer `X_BEARER_TOKEN`): `/2/users/by`, `/2/users/:id/tweets`, `/2/lists/:id/tweets`,
  `/2/tweets/search/recent`, `/2/users/:id/following`, using `tweet.fields=created_at,public_metrics,entities,
  author_id,referenced_tweets` and `expansions=author_id`.
- `XaiClient` (`XAI_API_KEY`): one Responses call per batch of up to 20 handles (`allowed_x_handles`,
  `from_date`), or per discovery query. Grok is asked for a JSON array of posts. Only posts whose status URL is
  in the citations are kept.
- `Budget`: per-run post/user read caps and a daily USD cap persisted in `meta.x_spend`. `charge()` refuses
  before a call when the projection exceeds a cap.
- `provider()` resolves `auto` → xapi if `X_BEARER_TOKEN`, else xai if `XAI_API_KEY`, else none.

**Ingestion** — every post → (a) items for each linked arXiv/GitHub/HF/URL (canonical id) with metrics
`x_likes`, `x_reposts`, `x_quotes`, `x_bookmarks` and `x_shares` (distinct accounts); (b) for posts without an
external link that look like announcements, a `post` item with id `x:<post id>`. Edge `entity —shared→ item`
with weight = post engagement.

**Expansion** — new handle kind `x` in `ENTITY_FETCHERS`; sweep `x` over watched accounts in batches
(bandit-selected like other entities) plus `x.lists` and `x.queries`. Follow graph: for the top-k yield accounts,
fetch `following` (capped, cached 30 days), then raise co-followed accounts' prior by
`1 - Π(1 - w_i)` over the followers' yields. `social()` gains X. GitHub `twitter_username` gives handle discovery.

**Scoring** — new quantitative feature `attention = 1 - exp(-Σ_sharers yield_s·(0.5 + centrality_s))`, with a
1.5× earliness boost when shared within 48h of publication. Prior weight 0.5; `traction` also includes X
engagement.

**Task graph**
1. T1 provider layer + budget (AC1, AC3, AC4)
2. T2 ingestion + sweep + entity fetcher + seeds/config (AC2)
3. T3 follow-graph/co-follow expansion + GitHub handle discovery (AC5)
4. T4 attention signal + traction (AC6)
5. T5 tests (AC1–AC7) + docs (AC8)
